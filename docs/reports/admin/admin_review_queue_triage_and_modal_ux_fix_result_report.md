## 改了什么

### A. 左侧列表更适合人工分拣

#### 1. 草稿卡片信息密度增强

每条卡片现在展示：

| 字段 | 旧版 | 新版 |
|------|------|------|
| 标题 | 有 | 有 |
| 时间 | 有 | 移入详情 header |
| "待人工确认" badge | 有 | 替换为风险等级 badge（严重/高/中/低） |
| 固定的"质量检查需要人工确认"文案 | 有 | 移除，替换为结构化信息 |
| 来源文件 | 仅 pill 形式 | **文件名** + 来源标签（截断过长的路径） |
| 风险等级 | 无 | **风险等级 badge**（右上角，CRITICAL/HIGH/MEDIUM/LOW 颜色编码） |
| 问题类型 | 无 | **问题类型标签**（最多展示 3 个 + 超过时显示 "+N"） |
| 问题数量 | 无 | **"N 个问题"** |
| 修复轮次 | 有 | 保留（"修复 1 / 2"） |

#### 2. 筛选/分组工具栏

在列表顶部新增筛选栏，所有筛选基于前端已拿到的数据，不需要额外后端接口：

- **按来源文件筛选**：下拉列出所有来源文件，选中后仅显示该来源的草稿
- **按风险等级筛选**：下拉列出 CRITICAL / HIGH / MEDIUM / LOW
- **按问题类型筛选**：下拉列出 false_provenance / missing_referential / conceptual_distortion 等
- **按来源分组**：勾选后同一来源文件的草稿聚合在一起，显示来源文件头（文件名 + 篇数），便于发现系统性同源问题

筛选状态在 `state.filters` 中维护，重新渲染时自动合并过滤条件。

#### 3. 快速切换体验

- **键盘导航**：选中列表后，↑↓ 方向键可快速切换到上一条/下一条草稿，自动滚动到可见区域
- 列表项 hover/选中态保持清晰的视觉反馈

### B. 右侧详情更适合人工判断

#### 详情区段重排（按审核优先级）

| 顺序 | 旧版 | 新版 |
|------|------|------|
| 1 | 草稿正文 | **审核概览**（风险等级 + 问题数量 + 问题类型 + 来源文件 + 更新时间） |
| 2 | 来源文件 | **待人工确认说明**（问题卡片列表，优先级前置） |
| 3 | 待人工确认说明 | **来源文件** |
| 4 | 处理轮次 | **草稿正文** |
| 5 | 按钮 | **处理轮次** |
| 6 | 技术详情（折叠） | **按钮** |
| 7 | — | **技术详情（折叠）** |

关键改动："待人工确认说明"移到"草稿正文"之前，让用户先判断"为什么被拦"，再看正文核对。

审核概览区使用左绿色边框突出显示，包含风险等级 badge、问题类型列表、来源文件等关键判断信息。

### C. 确认入库 / 驳回弹窗重做

#### 旧版问题
- 标题是问句式（"确认这篇草稿可以入库？"）
- 操作人输入框是视觉焦点
- 中间有孤立的白色横幅 hint 文字
- 只有标题、来源、hint、操作人四个扁平字段

#### 新版信息结构（四段式）

**标题**：确认入库 / 驳回草稿
**副标题**：草稿标题（粗体）

**第一组：为什么需要你确认**
- 风险等级 badge（颜色编码）
- 问题类型（中文化）
- 待确认问题数

**第二组：你现在要核对什么**（检查清单）
- 是否超出源文范围
- 是否新增源文未提供的主题或结论
- 来源文件是否足以支撑正文
- （驳回时）问题是否无法通过简单修正解决

**第三组：来源摘要**
- 来源文件名
- 更新时间

**第四组：操作记录**
- 操作人（降级为普通字段，不再是视觉焦点）
- 驳回时：驳回原因 textarea（带辅助提示："建议填写：超出源文范围 / 概念偏差 / 新增未提供内容 / 依据不足 / 数值矛盾"）
- 确认时：可选备注字段

**按钮层级**：
- 确认入库弹窗：取消 | 驳回（危险次按钮，在左侧） | 确认入库（主按钮）
- 驳回弹窗：取消 | 确认驳回（危险按钮）

各分组使用浅色面板包裹，清晰区分信息层级。

### D. 为什么本轮不做批量审批

1. 后端 `/api/v1/admin/compile/review-queue/{id}/approve` 和 `.../reject` 是单条接口，没有批量端点
2. 前端未伪造批量能力——没有 "批量确认" / "批量驳回" 按钮或 UI
3. 本轮通过分组/筛选/快速切换来降低逐条处理成本：同一来源的草稿聚在一起，用户可以连续快速判断同源的多篇，但每篇仍需独立 confirm
4. 代码中不含 `batchApprove`、`batch-approve`、`批量确认` 等字样（已通过 runtime 测试验证）

### E. 关键架构决策

1. **筛选/分组基于已有前端数据**：`getFilteredItems()` 在 `state.items` 上做 client-side filter，不触发额外 API 调用
2. **风险等级从 reviewIssuesJson 推导**：`resolveItemRiskLevel()` 解析 JSON 中的最高 severity，支持 CRITICAL 级别
3. **问题类型从 reviewIssuesJson 去重提取**：`resolveItemIssueTypes()` 返回去重后的 category 列表
4. **分组展示使用第一来源文件**：按 `sourcePaths[0]` 分组，同一来源文件下的草稿聚在一起
