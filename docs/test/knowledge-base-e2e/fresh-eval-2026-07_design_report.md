## 1. 第四套的目标能力清单

与前三套不同，第四套聚焦**多表关联、状态流转、时间窗口、周期计算**。核心验证以下 8 项新能力：

| # | 能力 | 前三套是否覆盖 | 第四套如何验证 |
|---|------|:---:|------|
| 1 | **设备台账与维护周期抽取** | PE2 有设备借用（借用天数），PE3 有合同期限，但都没有**定期维护周期**（如"每 3 个月维护一次"） | YAML 设备台账中包含各设备的维护周期、上次维护日期、下次维护到期日 |
| 2 | **巡检计划与故障工单的状态流转** | 未覆盖——前三套的数据都是静态快照，没有状态机 | CSV 工单列表含状态字段（待处理→处理中→已解决→已验收），验证状态流转查询（"哪些工单还在处理中"） |
| 3 | **故障等级与响应时限的关联** | PE3 有 SLA 指标表（响应时间），但没有故障等级→响应时限的映射 | XLSX 故障等级定义表（P0/P1/P2/P3 对应的响应时限、升级条件） |
| 4 | **多表关联查询**（设备→巡检→工单→处理记录） | PE3 有跨文档组合（合同+补充协议），但只是 2 文档冲突，不是多表关联 | 设备台账（YAML）↔ 巡检计划（XLSX）↔ 故障工单（CSV）三表关联，验证"某设备的最近一次故障是什么等级" |
| 5 | **时间窗口查询**（"本月到期"、"逾期未处理"） | 未覆盖——前三套的日期查询仅限于静态日期比较 | CSV 工单中的日期字段：创建时间、计划完成时间、实际完成时间，验证"超期未完成的工单" |
| 6 | **责任人 + 角色 + 部门的多维关联** | PE1 有 SL/TL/IM，PE2 有安全员/设备管理员，但都是单文档内的角色 | 跨文档的责任关联：设备台账中的"责任工程师" ↔ 工单中的"处理人" ↔ 巡检计划中的"巡检人" |
| 7 | **CSV 批量数据的聚合与排序** | PE2 有 CSV（维护计划表），PE3 有 CSV（付款计划），但都是简单查询 | 工单 CSV 含 15-20 条记录，验证聚合（"P0 工单占比"）、排序（"最近 5 条工单"）、分组（"按状态分组统计"） |
| 8 | **证据不足时的正确拒答** | 前三套均有覆盖 | "某设备的保修期到什么时候"——如果设备台账中未定义保修期，必须拒答，不能让维护周期抢占 |

## 2. 为什么它和前三套不同

| 维度 | PE1 | PE2 | PE3 | PE4 |
|------|-----|-----|-----|-----|
| **核心文档类型** | Markdown+YAML+PDF+XLSX | Markdown+YAML+XLSX+CSV+PDF | PDF×2+YAML+XLSX+CSV | **YAML+XLSX+CSV+Markdown** |
| **信息特征** | 静态事实 | 静态字段值 | 条款/百分比/冲突 | **状态机、时间窗口、周期、多表关联** |
| **数值类型** | 端口号、版本号 | 金额、天数 | 百分比、罚金、期限 | **周期（月）、间隔天数、工时、工单数量** |
| **逻辑复杂度** | 简单查找 | 单字段多实体 | 文档冲突、条件链 | **多表 JOIN、状态流转、时间范围过滤** |
| **最大新增风险** | — | — | — | 避免因为工单/设备数据引入"设备域特判"或"状态机硬编码" |
| **关键差异** | | | | **前三套验证"是什么"，第四套验证"现在是什么状态"和"下一步该做什么"** |

### 为什么用两份 XLSX

- `inspection-schedule.xlsx`：模拟定期巡检记录（20+ 行），验证表格日期范围查询
- `fault-severity-matrix.xlsx`：故障等级定义，验证等级→时限的映射和排序

### 为什么用 CSV 做工单

- `fault-work-orders.csv`：含 15-20 条工单——足够验证批量聚合、状态分组、时间窗口过滤，但不会因为数据量过大偏离"知识库检索"的验证目标

## 4. 推荐的 Source 类型与每类 Source 的作用

### 4.1 `01_markdown/medical-equipment-maintenance-policy.md`（维护总则）

**格式**：Markdown，约 2-3 个 section。

**内容要素**：
- 适用范围（哪些设备纳入维护管理）
- 维护周期定义（日检/周检/月检/季检/年检 的检查内容和责任人）
- 故障等级定义（P0 紧急/P1 高/P2 中/P3 低 的判定标准）
- 响应流程（故障上报→分级→派工→处理→验收）
- 角色定义（设备科负责人、责任工程师、巡检员、外部厂商）

**验证能力**：
- Markdown section 的内容归纳
- 故障等级→响应流程的因果关系
- 角色职责的区分

### 4.2 `02_structured/equipment-registry.yaml`（设备台账）

**格式**：YAML，含多台设备的嵌套结构。

**内容要素**：
```yaml
equipment:
  - id: "MRI-001"
    name: "核磁共振成像仪"
    category: "影像诊断"
    location: "影像楼 1F A区"
    responsible_engineer: "张工"
    maintenance_cycle_months: 3
    last_maintenance_date: "2026-04-15"
    next_maintenance_due: "2026-07-15"
    warranty_expiry: "2028-03-31"
    vendor: "西门子医疗"
    vendor_contact: "400-xxx-xxxx"
  - id: "CT-002"
    name: "64排螺旋CT"
    ...（共 8-10 台设备）
```

**验证能力**：
- YAML 嵌套路径精确查找（如 `equipment[0].maintenance_cycle_months`）
- 时间窗口查询（"本月到期维护的设备" —— 需比较 `next_maintenance_due` 与当前日期）
- 责任工程师关联
- 保修期 vs 维护周期的区分（防 sibling 抢占）

### 4.3 `03_xlsx/inspection-schedule.xlsx`（巡检计划表）

**格式**：XLSX，20+ 行。

**内容要素**：
| 巡检日期 | 设备ID | 设备名称 | 巡检类型 | 巡检人 | 结果 | 备注 |
|---------|--------|---------|---------|--------|------|------|
| 2026-06-01 | MRI-001 | 核磁共振 | 月检 | 张工 | 正常 | — |
| 2026-06-03 | CT-002 | 64排CT | 月检 | 李工 | 异常 | 球管温度偏高 |

**验证能力**：
- 表格条件查询（"6 月份的巡检记录有哪些"）
- 巡检结果统计（"异常巡检占比"）
- 巡检人查询（"李工巡检了哪些设备"）
- 与设备台账的关联（巡检表中设备 ID ↔ YAML 中 equipment id）

### 4.4 `03_xlsx/fault-severity-matrix.xlsx`（故障等级定义表）

**格式**：XLSX。

**内容要素**：
| 等级 | 名称 | 响应时限 | 解决时限 | 是否需要升级 | 升级条件 | 是否需停机 |
|-----|------|---------|---------|:---:|------|:---:|
| P0 | 紧急 | < 15 分钟 | < 2 小时 | 是 | 影响患者安全 | 是 |
| P1 | 高 | < 1 小时 | < 8 小时 | 是 | 影响诊断业务 | 否 |
| P2 | 中 | < 4 小时 | < 24 小时 | 否 | — | 否 |
| P3 | 低 | < 24 小时 | < 72 小时 | 否 | — | 否 |

**验证能力**：
- 等级查询（"P1 的响应时限是多少"）
- 多条件排序（"哪个等级需要停机"）
- 等级间的比较（"P0 和 P1 的升级条件有什么区别"）

### 4.5 `04_csv/fault-work-orders.csv`（故障工单列表）

**格式**：CSV，15-20 条。

**内容要素**：
| 工单号 | 设备ID | 故障等级 | 故障描述 | 创建时间 | 处理人 | 状态 | 计划完成 | 实际完成 |
|-------|--------|---------|---------|---------|--------|------|---------|---------|
| WO-042 | MRI-001 | P1 | 梯度线圈异常 | 2026-06-05 09:30 | 张工 | 处理中 | 2026-06-05 17:30 | — |
| WO-041 | CT-002 | P0 | 高压发生器故障 | 2026-06-04 14:00 | 李工 | 已解决 | 2026-06-04 16:00 | 2026-06-04 15:45 |
| WO-040 | CT-002 | P2 | 图像伪影 | 2026-05-28 10:00 | 王工 | 已验收 | 2026-05-29 18:00 | 2026-05-29 16:30 |

**验证能力**：
- 状态过滤（"处理中的工单"）
- 时间窗口查询（"超期未完成的工单" —— 计划完成 < now 且状态 != 已验收）
- 按等级聚合（"P0 工单数量"）
- 按设备聚合（"CT-002 的历史工单"）
- 责任人查询（"张工处理了哪些工单"）
- CSV 批量数据的排序（"最近 5 条工单"）

### 4.6 `05_pdf/emergency-repair-sop.pdf`（应急处置 SOP）

**格式**：PDF，1 页。

**内容要素**：
- P0 故障的应急处置流程（停机→通知→隔离→厂商到场→修复→恢复→验收）
- 各步骤的责任人和时限

**验证能力**：
- PDF 内容问答
- 与 XLSX 等级表的关联（"P0 故障除了响应时限，还有哪些处置步骤"）

## 7. 需要避免的过拟合与红线

### 7.1 过拟合风险

| 风险 | 第四套如何避免 |
|------|---------------|
| Writer 针对"设备台账"做特殊结构解析 | YAML 使用与 PE2/PE3 相同的 key_value_list 结构，不引入设备专属的 document type |
| query 层对"P0/P1/P2/P3"做硬编码等级映射 | 等级搜索依赖现有的混合脚本 token（如 PE2 的 "B级" 修复），不做等级语义映射 |
| 对"逾期"做时间比较特判 | "逾期"通过 CSV 中的日期字段和状态字段自然判断，query 不注入当前日期——依赖 LLM 的自然推理 |
| 对"WO-xxx"工单号做正则特判 | 工单号作为普通 ASCII token 被 QueryTokenExtractor 提取（含 `-` 的 ASCII pattern），不做工单号格式识别 |
| 对"维护周期 vs 保修期"做字段级区分 | FG1 的保护依赖 terminal unit sibling 不混淆（现有通用能力），不新增"如果是 warranty_expiry 则保护"逻辑 |
| 对"设备台账"做 table join | 不做跨表 JOIN——每题只验证单 source 或双 source 的 LLM 组合能力，不要求系统实现真正的多表关联查询 |

### 7.2 红线

- 题目、答案、设备名、工单号、等级、日期**不得写入 `src/main/java/**`、prompt、配置、SQL、scripts、allowlist**
- FQ9 逾期判断的**逻辑必须通用**（"状态+日期比较"），不能写成"当 source 含 fault-work-orders.csv 时做逾期检查"
- FG1 日期保护的**逻辑必须通用**（"不让 sibling 字段抢占"），不能写成"当字段名含 warranty 时特殊保护"
- 搜索词 `P0` 的短 token 匹配依赖现有的混合脚本 token 修复，不新增 P0 特判
- 搜索词 `WO-042` 的匹配依赖现有 ASCII token（含 `-`），不新增工单号格式识别
- 禁止做"设备域 entity 识别"——设备 ID 只是普通文本，不构建设备知识图谱
