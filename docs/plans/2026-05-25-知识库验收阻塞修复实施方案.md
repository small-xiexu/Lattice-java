## 1. 当前阻塞结论

### 1.1 真实阻塞表现

- 编译成功，但正式文章数为 `0`，只生成了 4 篇 `needs_human_review` 草稿。
- 4 篇草稿正文均接近 fallback 占位稿，只包含：
  - `title`
  - `summary`
  - `Sources`
- 草稿标题退化成：
  - `01 Markdown`
  - `02 Structured`
  - `=== Page`
  - `04 Office`

### 1.2 根因归纳

#### 根因 A：Graph 主链 Analyze 未接入 LLM

- `SourceIngestSupport` 当前通过 `new AnalyzeNode(null, null, compilerProperties)` 初始化 Graph 主链分析器。
- 这意味着 `AnalyzeNode.analyzeWithLlm(...)` 在真实编译链中永远不会运行。
- 结果：Analyze 只能依赖规则路径，规则未命中时直接退回 fallback 概念。

#### 根因 B：当前规则路径对“小型真实资料”覆盖不足

- 长文档 topic 拆分默认要求：
  - 长文档 `>= 12000` 字，或
  - 中等文档 `>= 6000` 字且标题数 `>= 5`
- 验收资料中的 Markdown / PDF / XLSX 都低于该门槛。
- 结构化表 overview 默认要求 `ROW_COUNT_THRESHOLD = 200`，当前 XLSX 仅 7 行，不触发。
- YAML / PDF / 小型 Office / 中短 Markdown 在当前规则链里都缺少“轻量主题提取”路径。

#### 根因 C：fallback 概念标题错误地优先使用分组键

- `GroupNode` 默认按顶层目录生成 `groupKey`，例如 `01_markdown`、`02_structured`。
- Analyze fallback 概念标题直接由 `groupKey -> toTitle(...)` 得到 `01 Markdown`、`02 Structured` 等目录名标题。
- 同时，源文件元数据中的 `documentTitle` 明明已经存在，但 fallback 概念没有优先使用。

#### 根因 D：writer fallback 对失败静默，不利于快速定位

- 当前 writer 在 LLM 编译失败或空返回时会静默走 `buildFallbackMarkdown(...)`。
- 主链没有显式暴露“本篇草稿是否来自 writer fallback”。
- 这不是本轮三大主修复项之一，但属于必须补充的最小可观测性要求。

## 2. 目标与验收口径

### 2.1 目标

- 让 Graph 主链的 Analyze 真正具备 LLM 分析能力，而不是固定停留在规则 fallback。
- 让 fallback 概念标题优先表达真实来源主题，不再默认暴露目录名。
- 为中短 Markdown、单页 PDF、小型 XLSX、少量 YAML 这类资料补上“轻量主题提取”能力，避免一上来就退回空概念。

### 2.2 完成标准

- 重新导入同一套验收资料后，不再出现 `01 Markdown / 02 Structured / === Page / 04 Office` 这类目录名或分页占位标题。
- 新生成的 `MergedConcept` 至少满足以下条件之一：
  - `description` 非空
  - `sections` 非空
  - `title` 来自真实文档标题而不是目录分组名
- Graph 主链运行时能够区分：
  - 结构化命中
  - 长文档 topic 命中
  - 小资料轻量提取命中
  - LLM analyze 命中
  - fallback 命中
- 本轮修复不得引入任何面向当前样例的业务硬编码。

### 2.3 通过后的最小业务结果

- 即使内容仍需人工确认，也必须先生成“可读草稿”，而不是目录名占位稿。
- 标题列表、搜索和问答后续回归应建立在“草稿已具备内容语义”的前提上。

### 2.4 分层验收口径

- `P4-A 草稿层验收`
  - 目标：验证本轮修复是否已经把“目录名占位稿”变成“可读草稿”。
  - 关注点：
    - 草稿标题是否具备主题语义
    - `description / sections / snippets` 是否不再同时为空壳
    - `analysisMode / titleSource / fallbackReason / writerFallbackUsed` 是否可解释
  - 说明：该层不要求文章已正式发布；只要系统设计仍要求人工确认，就以待确认草稿质量作为第一验收口径。

- `P4-B 发布后业务验收`
  - 前提：人工确认发布流程完成，正式文章可被检索和问答消费。
  - 关注点：
    - 搜索是否能命中正式文章
    - 标题优化是否真正进入最终知识条目
    - 问答是否建立在新的可读文章之上
  - 说明：若未完成发布，则不得用搜索或问答失败反推本轮 Analyze 修复失败。

## 3. 实施原则

### 3.1 通用性优先

- 所有修复都必须基于文档结构、元数据、标题层级、表格结构、内容长度、来源类型等通用信号。
- 不允许引入任何仅对当前验收资料成立的命名映射或词表。

### 3.2 先恢复 Analyze 主链，再补小资料路径

- 先修“Graph 主链 Analyze 永远不走 LLM”的装配问题。
- 再补小资料轻量提取路径。
- 最后修 fallback 标题来源和可观测性，避免边调边猜。

### 3.3 不把阈值调成样例特供

- 阈值可以调整，但必须写出通用依据。
- 如果调阈值的唯一理由是“让当前 2752 字 Markdown 刚好命中”，则视为无效方案。
- 更稳妥的方式是增加“小资料轻量提取”新路径，而不是粗暴下调长文档阈值。

### 3.4 术语澄清：这是 Analyze 概念生成优先级，不是标题生成顺序

- `STRUCTURED -> TABLE_OVERVIEW -> LIGHTWEIGHT_SMALL_DOC -> TOPIC -> LLM -> FALLBACK`
  表示的是 Analyze 阶段“如何产出概念”的优先级。
- 该顺序决定：
  - 是否先得到一个有语义的 `AnalyzedConcept / MergedConcept`
  - 该概念是否具备 `title / description / sections / snippets`
  - writer 后续是否有足够输入写成可读草稿
- fallback 标题来源优先级只是其中一个子问题，不能替代概念生成修复。

## 4. 修复项一：恢复 Graph 主链 Analyze 能力

### 4.1 目标

- 让 Graph 主链中的 `AnalyzeNode` 真正接入 `llmGateway` 与可用的 analyze prompt。
- 让真实编译链具备“结构化规则失败后，再走 LLM 分析”的能力。

### 4.2 现状问题

- 当前 `SourceIngestSupport` 初始化的 `AnalyzeNode` 使用 `null llmGateway`。
- 导致 `AnalyzeNode.analyzeWithLlm(...)` 逻辑存在但在 Graph 主链中不可达。

### 4.3 实施动作

1. 调整 `SourceIngestSupport` 中 `AnalyzeNode` 的装配方式  
   - 传入真实 `llmGateway`
   - 传入可用的 `schemaAwarePrompts` 或继续走现有默认 analyze prompt

2. 保持 Analyze 的既有优先级不变  
   - `STRUCTURED`
   - `TABLE_OVERVIEW`
   - `LIGHTWEIGHT_SMALL_DOC`
   - `TOPIC`
   - `LLM`
   - `FALLBACK`

3. 明确 Analyze LLM 的失败语义  
   - `LLM analyze` 失败不得阻断整批编译
   - 失败后继续后续通用路径或最终 fallback
   - 至少区分：
     - `SUCCESS`
     - `EMPTY_RESULT`
     - `PARSE_FAILED`
     - `TIMEOUT`
     - `ROUTE_UNAVAILABLE`

4. 补最小运行期可观测性  
   - 记录本轮概念来自哪条 analyze 路径
   - 至少区分 `STRUCTURED / TABLE_OVERVIEW / LIGHTWEIGHT_SMALL_DOC / TOPIC / LLM / FALLBACK`
   - 当 `LLM analyze` 失败时，额外落 `failureReason`
   - 落点优先选 `metadata_json`、编译步骤摘要或 working set 摘要，不新增长期业务表

### 4.4 红线约束

- 不允许为了当前样例新增专门的 analyze prompt 分支。
- 不允许按具体目录名、文件后缀组合直接生成固定概念标题。
- 不允许因为 LLM analyze 恢复了就删掉规则层。
- 不允许把 `LLM analyze` 失败写成“当前样例专用的兜底 prompt 切换”。

### 4.5 验收

- Graph 主链编译时，Analyze 具备真实 LLM 调用能力。
- 当规则路径未命中时，不再必然直接落到 fallback。
- 编译步骤或 working set 中可明确看到 analyze 路由结果。
- 当 `LLM analyze` 超时、空返回或解析失败时，编译仍能继续，并留下 `failureReason`。

### 4.6 状态

- 状态：`已完成`
- 备注：`SourceIngestSupport` 已接回真实 `llmGateway + SchemaAwarePrompts`；`analysisMode / failureReason` 已贯穿 concept working set 与 article `metadata_json`；`scan-redline`、`compile` 与定向测试已通过。

## 5. 修复项二：修正 fallback 标题来源优先级

### 5.1 目标

- 即使 Analyze 最终 fallback，也要优先使用“真实来源标题”，而不是目录分组名。

### 5.2 现状问题

- 当前 fallback 概念标题直接取 `groupKey -> toTitle(...)`。
- `groupKey` 默认来自顶层目录，因此目录结构污染了知识标题。
- 源文件元数据已有 `documentTitle`，但没有进入 fallback 标题优先级。

### 5.3 实施动作

1. 为 Analyze fallback 概念新增通用标题优先级  
   - 单来源时：
     - `source_file.metadata.documentTitle`
     - 文件名去扩展名
     - `groupKey`
   - 多来源时：
     - 若来源标题或轻量概念可归纳出稳定共同主题，则用共同主题
     - 若无法稳定归纳共同主题，则退到中性概括标题，而不是直接暴露目录名
     - 中性概括标题必须来自通用结构信号，不得拼接样例词

2. 将 `groupKey` 保留为内部归组语义  
   - 可继续用于 conceptId / batch grouping
   - 但不应默认作为用户可见标题

3. 为 fallback 标题补来源说明  
   - 在 `metadata_json` 中写明：
     - `analysisMode`
     - `titleSource`
     - `fallbackReason`
     - `sourceCount`

### 5.4 红线约束

- 不允许写“如果目录名是 `01_markdown` 就取 Markdown 文档标题”的样例特判。
- 不允许对 `pdf/xlsx/yaml/md` 分别写固定标题模板，只允许写通用优先级规则。
- 不允许把当前验收资料的 `documentTitle` 写进代码或配置。
- 多来源标题归纳只能依赖标题、文件名、结构摘要等通用信息，不得读取题集或问答结果反向命名。

### 5.5 验收

- 单来源 fallback 概念不再默认显示目录名。
- 当 `documentTitle` 存在时，标题应优先来自真实文档标题。
- 当前样例中不再出现 `01 Markdown / 04 Office / 02 Structured` 作为最终主标题。

### 5.6 状态

- 状态：`已完成`
- 备注：fallback 标题已改为单来源优先 `documentTitle -> 可读 file stem -> groupKey`，多来源在无法稳定归纳共享标题时退到中性标题；`titleSource` 已贯穿 `AnalyzedConcept / MergedConcept / article metadata_json`，并补 `fallbackReason` 落点；`scan-redline`、`compile` 与 `AnalyzeNode / CrossGroupMergeNode / CompileArticleReviewFlow / StateGraph / document parse` 定向测试已通过。

## 6. 修复项三：新增“小资料轻量主题提取”路径

### 6.1 目标

- 为中短 Markdown、单页 PDF、小型 XLSX、少量 YAML 这类资料增加通用主题提取路径。
- 避免它们因为够不上“大文档/大表格阈值”而直接退回空概念。

### 6.2 现状问题

- 当前规则路径偏向：
  - 大文档 topic 拆分
  - 大表格 overview
  - 结构化 JSON 概念
- 对单文件、小规模、但内容明确的资料缺少“生成一个高质量单概念”的能力。
- 对“多来源、同主题、但每个来源都很小”的资料缺少稳定处理策略，例如少量 YAML/配置文件被同批分组后直接落成目录名概念。

### 6.3 设计原则

- 只做通用结构提取，不做资料类型专属样例规则。
- 单概念提取的输入信号只能来自：
  - `documentTitle`
  - 首段正文
  - heading 结构
  - page/sheet marker
  - structured table metadata
  - 前若干条高信息量内容行
- 多来源小资料默认优先逐源产出轻量概念，再交给 merge 决定是否合并。
- 只有在多来源间的结构信号高度一致时，才允许直接生成一个共享轻量概念。

### 6.4 建议实现路径

#### 路径 A：单来源文档概览概念

适用条件：

- 单来源
- 未命中长文档 topic 拆分
- 未命中大表格 overview
- 但正文长度、标题、首段或结构化行足以构成主题

产出要求：

- `title`：优先取 `documentTitle`
- `description`：取首段或首批高信息量行归纳
- `sections`：至少构造 1 个 section，而不是空数组
- `snippets`：保留来源正文前部或结构化高信息量片段

#### 路径 B：小型结构化资料概览概念

适用条件：

- 单来源，或少量同主题多来源的结构化表格 / YAML / 配置文本
- 行数或字符数不够大表阈值
- 但具备明确字段、列头、键值或配置项

产出要求：

- 用列头、键名、首批记录构建概览 section
- 把精确值保留在 `contentLines` 中
- 不允许只生成 `Sources` 列表

#### 路径 C：多来源小资料逐源轻量概念

适用条件：

- 当前 batch 内存在多个小来源
- 单个来源都不足以触发 `TABLE_OVERVIEW` 或 `TOPIC`
- 但强行合并会丢失标题语义，或只能退化成目录名

处理策略：

- 默认策略：逐源生成 `LIGHTWEIGHT_SMALL_DOC` 概念
- 合并策略：仅当来源类型一致，且标题、键集合、列头或 heading 结构高度重合时，才允许在 Analyze 内提前合并
- 元数据要求：
  - 标记 `multiSourceLightweight = true/false`
  - 若合并，记录 `mergeBasis`，只允许写通用结构依据，如“shared_keys”“shared_headings”“shared_table_schema”

### 6.5 推荐插入顺序

建议放在 `structuredConcepts`、`structuredTableOverviewConcepts` 之后，并固定早于 `TOPIC / LLM / FALLBACK`。  
本方案明确采用以下 Analyze 概念生成优先级：

1. 结构化概念
2. 大表格 overview
3. 小资料轻量主题提取
4. 长文档 topic 拆分
5. LLM analyze
6. fallback

理由：

- 小资料路径本质上是低成本规则提取，应该早于高成本 LLM analyze。
- 该路径专门覆盖“够不上长文档，但明显有主题”的资料空档。
- 该路径早于 `TOPIC`，是为了避免中短资料被长文档门槛直接排除。

### 6.6 红线约束

- 不允许写“Markdown 资料默认叫手册”“PDF 资料默认叫参考”“Office 默认叫 checklist”这类模板映射。
- 不允许依据当前样例中的列名、阶段名、角色名定制抽取逻辑。
- 只能使用标题、首段、列头、键值、sheet/page marker 这类通用结构信号。
- 多来源提前合并只能依赖结构一致性，不得因为目录名相同就默认合并成一个概念。

### 6.7 验收

- 单页 PDF 生成的概念不再是 `=== Page`。
- 小型 XLSX 生成的概念不再是 `04 Office`。
- 中短 Markdown 至少生成一个带 `description` 或 `sections` 的主题概念。
- 少量 YAML / 配置文件在同批场景下，不再默认退化成单个目录名概念。
- 生成出的概念正文不再只有 `title + summary + Sources`。

### 6.8 状态

- 状态：`已完成`
