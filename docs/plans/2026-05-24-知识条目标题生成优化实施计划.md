# 知识条目标题生成优化实施计划

**文档版本**：v1.0  
**编写日期**：2026-05-24  
**适用仓库**：`/Users/sxie/xbk/Lattice-java`  
**定位**：本文是“已入库内容标题生成优化”的唯一执行台账。后续方案落地、断点恢复、验收回写只更新本文。  
**触发背景**：当前长文档切分后的知识条目标题直接复用切分锚点标题，容易出现“标题过泛、不能代表切分块整体内容”的问题；目标是把标题优化为更能代表切分后整段内容的表达，同时保留来源文档标题与原切分标题，避免信息丢失。

## 0. 台账规则与目标边界

### 0.1 台账规则

- 每完成一个可独立验收的事项，立即在本文回写为已完成，不允许等到阶段末统一勾选。
- 未完成事项必须写明 `进行中 / 阻塞 / 待验证` 之一，并补最小备注：做到哪、卡在哪、下一步是什么。
- 未经验证的事项禁止勾选完成。
- 若执行过程中发现设计前提失效，先回写本文，再调整方案，不允许只改代码不留痕。

### 0.2 状态约定

- `未开始`：尚未动工。
- `进行中`：已开始，需写明做到哪。
- `待验证`：实现完成但验收未完成。
- `阻塞`：无法继续，需写明原因和下一步。
- `已完成`：已实现且通过验收。

### 0.3 目标

- 让长文档切分后的知识条目标题，优先表达“该切分块整体讲什么”，而不是仅复用一个过泛的小节名。
- 同时保留“来源文档标题”和“原切分标题”，确保可追溯、可解释、可回看。
- 方案必须优先使用确定性规则，LLM 只作为低置信度兜底，不允许把全部标题生成都外包给 LLM。
- 不为具体业务文档、具体文件名、具体术语、具体样例问题写硬编码特判。

### 0.4 不在本计划范围

- 不改 Query / 检索 / 回答主链逻辑。
- 不改知识正文生成策略，不以“重写正文摘要”替代标题优化。
- 不引入新的长期独立表结构；优先复用 `metadata_json` 承载新增标题元数据。
- 不在本轮做前端整体视觉改版，只做标题与元信息呈现优化。
- 不做针对特定资料的专用标题模板或人工白名单。

### 0.5 红线

- 禁止根据具体文档名、业务域、题集、样例字符串生成专属标题逻辑。
- 禁止为了某个 bad case 在 Java 主链硬编码泛化标题黑名单之外的业务词特判。
- 禁止把“LLM 能生成得更像人话”当作全量走 LLM 的理由；必须先有规则层。
- 禁止只改前端展示文案，不保留结构化的 `sourceTitle / anchorTitle / representativeTitle` 数据。
- 当前项目按新数据从 0 到 1 重构推进，本计划不考虑历史回填、旧数据兼容或存量标题重建。

### 0.6 红线门禁

- 每轮涉及标题生成、标题展示的代码改动前，必须先运行 `bash scripts/scan-redline.sh`。
- 只有 `BLOCKER=0` 时，才能继续后续测试、回归和接口/页面联调。
- 任何希望“放宽门禁”的做法都不允许，包括修改脚本本身、扩大 allowlist、删除扫描规则或绕过扫描结果。
- 若红线扫描出现新增命中，先停在本计划中回写原因，再决定是收回改动还是继续收敛实现，不允许带着红线问题进入下一步。

## 1. 当前现状快照（2026-05-24）

### 1.1 当前标题生成链路

- 长文档切分由 `DocumentTopicConceptSegmentationSupport` 完成；当前 `TopicSegment` 的标题直接来自切分命中的标题行。
- `toAnalyzedConcept(...)` 直接使用 `topicSegment.title` 作为 `AnalyzedConcept.title`。
- 后续 `MergedConcept.title` 沿用该标题，`CompileArticleNode.compileDraft(...)` 又直接把 `mergedConcept.getTitle()` 写入 `ArticleRecord.title`。
- 管理端列表和详情当前都直接展示 `articleRecord.getTitle()`，没有同时暴露“源文档标题”和“切分原标题”。

### 1.2 当前已存在但未打通的来源标题能力

- 资料上传侧已有 `BundleSummary.displayName` 与 `BundleSummary.titleHints`，可作为资料源级标题候选。
- `source_files.metadata_json` 已保留源文件解析元数据，具备继续扩展单文件级 `documentTitle` 的空间。
- 文章 `metadata_json` 当前仅保存少量 description / structured / sourceCount / snippetCount / sectionCount，尚未保存标题生成上下文。

### 1.3 当前问题的真实表现

- 当切分标题本身是“下一步计划 / 说明 / 总结 / 其他 / 附录”这类泛化标题时，列表页标题无法概括整段内容。
- 用户需要点开详情才知道这段到底在讲什么，列表浏览效率低。
- 当同一来源文档下有多个泛化标题时，列表上会出现多个相似或重复感很强的条目，难以区分。
- 标题生成链路没有“代表性”置信度概念，无法判断某个标题是高质量的自然概括，还是仅仅因为切分规则命中了一个 heading。

## 2. 目标设计总览

### 2.1 标题数据模型

本期新增并统一以下四个概念：

- `sourceTitle`
  - 含义：来源文档标题。
  - 来源优先级：源文件 metadata 中的文档标题 > 资料源 `bundleSummary.displayName/titleHints` > 文件名（去扩展名）。

- `anchorTitle`
  - 含义：切分命中的原标题，即当前 `topicSegment.title`。
  - 作用：保持可追溯，不参与用户侧主展示优先级。

- `representativeTitle`
  - 含义：基于切分块整体内容生成的“代表性标题”。
  - 作用：作为用户侧主标题候选。

- `titleGenerationMode`
  - 含义：标题生成方式。
  - 枚举建议：`ANCHOR_DIRECT`、`RULE_BASED`、`LLM_FALLBACK`、`LEGACY_UNSET`。

### 2.2 页面展示目标

- 列表页主标题：优先展示 `representativeTitle`。
- 列表页辅助信息：展示 `来源：sourceTitle`、`切分标题：anchorTitle`。
- 详情页标题区：同时展示
  - 当前知识条目标题
  - 来源文档标题
  - 切分原标题
  - 标题生成方式

### 2.3 为什么不建议直接固定成 `源标题（切分标题）`

- `源标题（切分标题）` 只解决“知道它来自哪篇文档哪一段”，不解决“这段整体讲什么”。
- 当 `anchorTitle` 本身过泛时，`源标题（下一步计划）` 仍然不能帮助用户快速理解内容。
- `源标题` 往往较长；若强制拼接到主标题，会牺牲列表可读性。
- 更合理的方式是：主标题表达内容主题，来源与锚点作为辅助追溯信息。

## 3. 总体方案：规则优先 + LLM 兜底

### 3.1 方案原则

- 一级目标：稳定、可解释、可回归。
- 二级目标：尽量不增加编译成本。
- 三级目标：在标题泛化时再换取更好的语义表达。

### 3.2 三层生成策略

#### 第一层：锚点直用

适用条件：

- `anchorTitle` 语义完整，不属于泛化标题。
- `anchorTitle` 长度、词汇密度、信息量满足阈值。
- `anchorTitle` 与该 segment 的前部内容、子 section 标题具备较高一致性。

输出：

- `representativeTitle = anchorTitle`
- `titleGenerationMode = ANCHOR_DIRECT`

#### 第二层：规则归纳

适用条件：

- `anchorTitle` 属于泛化标题，或信息量明显不足。
- 但 segment 内部存在足够结构化信号，可通过规则稳定提炼主题。

输入来源：

- `sourceTitle`
- `anchorTitle`
- segment 前 1 段或前若干行正文
- segment 内部 section headings
- segment 前若干高信息量内容行
- segment 的 referential / path / URL / 枚举 / 列表结构信号

输出：

- 生成一个更能概括整段内容的 `representativeTitle`
- `titleGenerationMode = RULE_BASED`

#### 第三层：LLM 兜底

适用条件：

- `anchorTitle` 过泛。
- 规则归纳后仍然过于抽象、重复或低置信度。
- 当前 segment 较长、主题不集中，规则很难稳定压缩成一句标题。

输出：

- 使用 LLM 生成 `representativeTitle`
- `titleGenerationMode = LLM_FALLBACK`

### 3.3 为什么必须是“LLM 兜底”而不是“LLM 主路径”

- 全量走 LLM 会显著放大长文档编译成本。
- 标题会随模型版本、温度、prompt 微调产生漂移，难以稳定回归。
- 规则可覆盖相当一部分常见情况，尤其是结构良好的 Markdown / 文档说明类内容。
- LLM 更适合处理“规则无法可靠概括，但内容又确实值得更好标题”的少数情况。

## 4. 规则层详细设计

### 4.1 泛化标题识别

建立通用“泛化标题”识别器，但只允许识别**通用语义弱标题**，不允许引入业务词表。

候选规则：

- 长度过短且词义抽象，如 2-6 字的概述类标题。
- 命中通用弱标题集合：
  - `概述`
  - `说明`
  - `总结`
  - `附录`
  - `其他`
  - `备注`
  - `计划`
  - `方案`
  - `背景`
  - `问题`
  - `结论`
  - `下一步`
  - `下一步计划`
- 标题中的名词/动作密度过低。
- 标题无法从同段正文前 80-120 字中找到足够多的词汇支撑。

验收要求：

- 该识别器只能基于通用语言结构与通用弱标题词工作，不允许写业务术语黑白名单。

### 4.2 规则归纳输入裁剪

规则归纳不直接消费整段全文，避免噪声过大。建议只采样：

- `anchorTitle`
- `sourceTitle`
- segment 起始正文前 3-5 条有效内容行
- 前 2-4 个 section heading
- 前 200-400 字正文摘要窗口

这样既保留主题线索，也避免被超长正文拖偏。

### 4.3 规则归纳产出模式

建议支持以下通用模式：

#### 模式 A：对象 + 动作

适用于正文集中描述某个对象在做什么、要求什么、如何处理。

示例形态：

- `向量索引重建触发与状态校验`
- `Dashboard 状态摘要接入与人工确认联动`

#### 模式 B：对象 + 范围 + 约束

适用于规约、清单、治理规则类 segment。

示例形态：

- `质量台账更新范围与回写要求`
- `编译阶段失败处理与回退约束`

#### 模式 C：主题 + 子主题集合

适用于正文由多个并列小点组成，但可归属到同一主题。

示例形态：

- `质量打磨进展、当前焦点与后续推进要求`
- `资料导入现状、问题归因与下一步处理`

### 4.4 规则归纳置信度

规则层必须输出一个简化置信度，用于决定是否触发 LLM：

- `HIGH`
  - 可直接采用
- `MEDIUM`
  - 可采用，但允许后续灰度观察
- `LOW`
  - 触发 LLM 兜底

建议判断信号：

- 标题中是否出现明确对象名词
- 标题与正文前部词汇重合度
- 标题是否仍命中泛化词
- 标题长度是否过短或过长
- 不同提炼信号之间是否冲突

## 5. LLM 兜底设计

### 5.1 触发条件

- 仅在规则层置信度为 `LOW` 时触发。
- 不因“想让标题更好看”触发。
- 不因来源文件类型不同而强制触发。

### 5.2 输入上下文

只喂最小上下文，避免成本膨胀：

- `sourceTitle`
- `anchorTitle`
- segment 前 200-400 字压缩内容
- 前若干 `section headings`

禁止直接喂整篇长文全文。

### 5.3 输出要求

LLM 输出必须是强约束单字段结果：

- 只输出一个中文标题
- 目标长度 12-28 字
- 必须能概括该切分块的主体对象与核心动作
- 不得使用“关于 / 相关说明 / 内容介绍 / 其他事项”这类空泛表述
- 不得引入正文中不存在的新信息
- 不得复述来源文件名替代内容概括

### 5.4 调用方式建议

- 不单独开新模型路由，优先复用编译链已有 writer 路由或一个轻量 title scene。
- 若后续成本高，可进一步拆出轻量模型绑定，但不作为第一阶段前置。

### 5.5 稳定性约束

- 默认温度接近 0，优先稳定。
- 必须保留 `titleGenerationMode=LLM_FALLBACK`，便于后续审计与回填。
- 生成失败时必须回退到规则标题，而不是中断整篇入库。

## 6. 数据结构与落盘设计

### 6.1 首选：复用 `metadata_json`

本期不新增列，先把标题增强信息写入 `articles.metadata_json` 与 `article_snapshots.metadata_json`。

建议结构：

```json
{
  "titleProfile": {
    "sourceTitle": "quality-progress-and-lessons",
    "anchorTitle": "下一步计划",
    "representativeTitle": "质量打磨阶段后续推进重点与台账更新要求",
    "titleGenerationMode": "RULE_BASED",
    "titleGenerationConfidence": "HIGH",
    "titleGenerationVersion": "v1"
  }
}
```

### 6.2 `title` 字段策略

- `articles.title`：保存最终用户主展示标题，即 `representativeTitle`。
- `anchorTitle` 不再直接覆盖 `title`，而是写入 metadata。
- `sourceTitle` 也不写入 `title`，而是作为辅助展示字段保留。

### 6.3 源文件元数据补强

优先把单文件级来源标题保存在 `source_files.metadata_json` 中，例如：

```json
{
  "documentTitle": "quality-progress-and-lessons",
  "bundleSummary": {
    "...": "..."
  }
}
```

来源优先级建议：

1. 单文件 metadata 中的 `documentTitle`
2. 资料源 `bundleSummary.displayName`
3. `bundleSummary.titleHints[0]`
4. 相对路径文件名去扩展名

### 6.4 未来可演进空间

- 若后续查询、筛选、排序要深度使用 `sourceTitle / anchorTitle / titleGenerationMode`，再评估是否加独立列。
- 本期先不动 schema，避免把标题优化升级成数据库演进项目。

## 7. 编译链路改造设计

### 7.1 源标题采集

目标：让 `RawSource` 或其 metadata 中尽可能携带单文件级 `documentTitle`。

实施方向：

- 文本文件：优先取 frontmatter `title` 或首个顶级标题。
- Office/PDF/解析服务输出：优先读取文档解析元数据中已有标题字段；没有则回退文件名。
- 上传资料包：保留 `bundleSummary.displayName/titleHints` 作为资料源级候选，但不直接替代单文件标题。

### 7.2 长文档切分阶段

当前：

- `TopicSegment.title` 只保留切分标题。

改造后：

- `TopicSegment` 保持当前字段不动或最小扩展。
- 在 `toAnalyzedConcept(...)` 阶段补充标题画像构建逻辑：
  - 读取 `sourceTitle`
  - 读取 `anchorTitle`
  - 运行规则归纳
  - 视置信度决定是否触发 LLM
  - 生成最终 `representativeTitle`

### 7.3 `AnalyzedConcept / MergedConcept` 承载

本期建议最小改法：

- `title` 字段承载最终 `representativeTitle`
- `description` 继续沿用现有语义
- `snippets/sections` 不变
- 标题画像附加信息通过新增 metadata carrier 或附加对象向后传递，最终写入 `ArticleRecord.metadataJson`

若当前领域对象不方便加字段，则可在 compile 阶段单独构建 `titleProfile`，不强行污染所有领域对象构造器。

### 7.4 `CompileArticleNode` 落库

改造要求：

- `ArticleRecord.title` 写最终展示标题
- `buildMetadataJson(...)` 扩展写入 `titleProfile`
- fallback markdown frontmatter 中的 `title` 也同步写最终展示标题

### 7.5 增量编译要求

增量场景需明确：

- 新增量写回时，必须直接产出完整 `titleProfile`
- 不允许把标题画像生成延后到单独回填任务
- 读取侧仍允许测试夹具或人工构造数据缺少 `titleProfile`，但主链生成结果必须完整

## 8. 接口与前端改造设计

### 8.1 管理端 API 返回结构

建议在列表与详情响应中新增字段：

- `sourceTitle`
- `anchorTitle`
- `representativeTitle`
- `titleGenerationMode`

其中：

- `title` 继续保留，语义为当前主展示标题
- `representativeTitle` 可等于 `title`，便于前端少推断

### 8.2 列表页展示调整

目标：

- 第一眼先看到“这条内容讲什么”
- 第二眼再看到“它来自哪篇文档”

建议展示：

- 主标题：`title`
- 副信息：`来源：sourceTitle`
- 补充信息：`切分标题：anchorTitle`

### 8.3 详情页展示调整

详情页新增一个“标题来源”说明块：

- 当前标题：`representativeTitle`
- 来源文档标题：`sourceTitle`
- 切分原标题：`anchorTitle`
- 生成方式：`titleGenerationMode`

### 8.4 搜索兼容

搜索仍应同时命中：

- `title`
- `sourceTitle`
- `anchorTitle`
- `conceptId`
- `sourcePaths`

避免“用户明明记得原小节叫‘下一步计划’，改造后却搜不到”。

本期优先：

- 先通过后端 query matching 把 metadata 里的 `sourceTitle / anchorTitle` 纳入匹配。
- 若代价太大，至少先在前端对列表结果做二次本地关键词高亮不是合格替代，不建议只做前端补丁。

  - 覆盖 `titleProfile` 序列化/反序列化

### 10.2 集成测试

- 长文档切分后标题落库
  - 验证 `articles.title`
  - 验证 `articles.metadata_json.titleProfile`
- 管理端列表接口
  - 验证新增字段可返回
- 管理端详情接口
  - 验证新增字段可返回
- 历史回填 dry-run / real-run
  - 验证不改正文、不改 sourcePaths

### 10.3 页面验收

- 列表页出现泛化标题样本时，主标题能明显比现状更贴近整段内容。
- 详情页能看到完整标题来源链路。
- 搜索原切分标题、来源文档标题、最终代表标题都能命中目标条目。

### 10.4 质量验收指标

建议抽样人工评估以下指标：

- `标题可理解率`
  - 人工看标题即可大致知道内容主题的比例
- `标题区分度`
  - 同一来源下不同切片不再大量重名/近似重名
- `标题忠实度`
  - 标题未引入正文中不存在的新结论
- `LLM 使用率`
  - 进入 `LLM_FALLBACK` 的比例应受控，不能过高

### 10.5 最低通过门槛

- 抽样 30 条新生成长文切片，人工判定“主标题能代表该切片整体内容”的通过率 `>= 80%`
- 其中 `LLM_FALLBACK` 占比建议 `<= 30%`
- 不允许出现“标题更好看了，但错概括了内容”的明显忠实度回退
- 每轮实现后必须先通过 `bash scripts/scan-redline.sh`，且 `BLOCKER=0`，才允许进入后续测试与回归

## 13. 风险清单

### 13.1 规则过强，误伤强标题

- 风险：把本来就很好的 `anchorTitle` 错判为泛化标题，反而生成更差标题。
- 应对：先保守识别；只有低信息量标题才进入规则归纳。

### 13.2 LLM 生成标题过度抽象或引入新信息

- 风险：看起来更自然，但不忠实于正文。
- 应对：强约束 prompt + 低温度 + 标题忠实度抽样验收。

### 13.3 搜索召回回退

- 风险：只搜索新标题命中，旧切分标题搜不到。
- 应对：把 `sourceTitle / anchorTitle / representativeTitle` 全部纳入搜索文本。

### 13.4 编译耗时增加

- 风险：长文档切片数多时，标题生成拖慢入库。
- 应对：绝大多数样本走规则层；仅低置信度片段走 LLM。

## 14. 建议实施顺序

建议严格按以下顺序推进，不要跳步：

1. 固化样本集与 `titleProfile` 契约
2. 打通 `sourceTitle`
3. 实现泛化标题识别器
4. 实现规则归纳器
5. 落库 `titleProfile`
6. 管理端 API 与页面展示
7. 再接 LLM 兜底

原因：

- 如果先上 LLM，容易掩盖规则层应解决的问题。
- 新数据项目不需要为历史重建预留额外复杂度，优先把主链标题质量和管理端体验做稳定。

## 15. 当前结论与下一步

- 当前方案已确认采用：**规则优先 + LLM 兜底**。
- 当前不采用：全量 LLM 标题生成，也不采用唯一展示 `源标题（切分标题）`。
- 下一步建议从 `P0` 开始，先补样本集和 `titleProfile` 契约，再进入编码实现。
